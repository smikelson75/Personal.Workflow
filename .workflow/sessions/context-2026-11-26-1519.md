## Existing Solution
- Workflow Core is Markdown skills and agents plus dependency-free Node `.mjs` tools tested with `node:test`; `workflow-check` checks Workflow Folder artifacts only and reads no Conversation Logs or git history.
- `.github/prompts/review-incubate.prompt.md` is a hand-run review of `/incubate` Conversations from Copilot `events.jsonl` logs; the Developer also keeps hand-written per-skill reviews (`docs/research/incubate-session-review.md`) that grow every session and cover only `incubate` and `brain-storm`.
- Artifacts link through `Builds on`, product slugs, plan paths, and commit scopes; no commit marker names the Harness.
- The Launch Script starts both Harnesses with `--add-dir <Home Repo>`, so every Home-layout Conversation can write to the Home Repo without a path prompt; the Update Script installs `.github/tools/` with Workflow Core.
- Copilot CLI and Claude Code both keep local Conversation Logs that identify the repo folder, skills, agents, and token use; Claude Code logs also show hooks. All 1,343 lines in 35 local Claude Code logs parsed; that format is undocumented.

## Problem
- Hand-kept skill reviews are unreadable, grow without bound, cost Developer time, and cover only two skills, so workflow parts are not improved with evidence.
- Desired outcome: workflow parts (skills, agents, hooks, scripts, instructions) improve over time so the workflow stays fresh, clean, token efficient, and easy to use, with each improvement's impact visible.

## Users
- `Developer` - the only reader of the Executive Summary and Ledger; runs both skills by hand and approves every change to a part.

## Workflow
- trigger: `pull-work` Phase completion prints a one-line nudge; the Developer runs `/skill-review` after any Phase or after all Phases.
- key step: `/skill-review` in a Home-layout Project Repo reviews every unreviewed skill use and Handoff since the last run, escalating one Depth at a time, and writes the Executive Summary, Ledger, and Review Record into the Home Repo.
- alternate path: `/skill-review <skill>` reviews only that skill's unreviewed uses and its pending Handoffs.
- key step: in `Personal.Workflow`, `/apply-observation` lists confirmed Observations; the Developer picks, approves at one Checkpoint, and the skill commits each change, marks it changed, and runs the Update Script.
- alternate path: `/apply-observation undo O<n>` reverts one applied Observation and makes it confirmed again.
- failure path: a Handoff with one end missing -> pending until a later run has both ends.
- failure path: a change failing its checks -> not committed; the Observation stays confirmed with the reason shown.
- successful outcome: a later `/skill-review` reports each applied Observation as improved or unchanged.

## Decisions
- rejected: automatic runs at Phase completion - the Developer starts every run.
- rejected: one document for the Developer and the agent - their purposes differ.
- rejected: re-reading already-reviewed Conversations on request - nothing is counted twice.
- rejected: fixed attribution of Handoff Observations to the writing skill - either side can cause a miss.
- rejected: dismissing requirements misses - a repeat shows a question gap.
- rejected: per-Project-Repo records, or running only from `Personal.Workflow` - findings must build up in one place where the Developer works.
- rejected: one commit per `/apply-observation` batch - a bad change must be revertible alone.
- rejected: names `Session Review` and `Workflow Review` - clash with `Session` and overstate scope; `Tier` and `Grade` for the cost levels - clash with Card `Tier` and read as seriousness.
- parked: incident tracing on request - the Handoff review traces most reopens over time.
- parked: trend views beyond Observation state - no need shown.
- parked: copy-layout Project Repos - no central place to write.
- parked: quality-word side fix in `brain-storm` and `incubate` - left for `/skill-review` to find and propose (R56).
