## Existing Solution
- Personal.Workflow repo: no application code; holds `AGENTS.md` and skills including `brain-storm` and `behavior-spec`, under `.github/skills/`.
- Session and Glossary formats are defined in `brain-storm/references/`; the spec format in `behavior-spec/references/`.
- No Workflow Folder existed before this session; this is the first Session.
- Touches: a new `workflow-check` tool; the `brain-storm` write step; the `behavior-spec` input-validation step.

## Problem
- Constant replanning because workflow documents miss critical detail, contradict each other, or carry excess information that confuses agent sessions.
- Desired outcome: catch these failures cheaply, before they reach later stages.

## Users
- `Skills/agents` (primary) - brain-storm and behavior-spec; need a fast, token-cheap gate they can act on.
- `Developer` (secondary, equally important) - runs it by hand for a health check.
- `CI` - runs it non-interactively; fails the build on errors.

## Workflow
- trigger: brain-storm finishes writing a Session and Glossary -> runs workflow-check on its new Session -> fixes all errors, considers warnings.
- trigger: behavior-spec validates inputs -> runs workflow-check on the Workflow Folder -> any error -> stop and redirect to brain-storm.
- trigger: developer or CI runs workflow-check on the Workflow Folder -> full report; CI fails on any error.
- warnings only -> run passes; findings still reported.
- successful outcome: zero error Findings; agents proceed.

## Requirements
- R1 - workflow-check reads the whole Workflow Folder of a target repo and reports Findings for Sessions and the Glossary. Accept: a Workflow Folder with known breaks reports each as a Finding.
- R2 - Structure Rules flag a Session or the Glossary missing parts its format requires. Accept: a Session with no Status yields a `structure` error.
- R3 - Chain Rules flag Sessions that disagree with each other (reused R#, retirement of an unknown ID, broken Builds on/Supersedes link). Accept: two Sessions defining R3 yield a `chain` error.
- R4 - Vocabulary Rules flag Sessions that disagree with the Glossary (avoid-synonyms, retired terms, Language-section terms absent from the Glossary). Accept: a Session using a listed avoid-synonym yields a `vocabulary` Finding.
- R5 - Excess Rules flag oversized documents and detail belonging to another stage. Accept: a Session naming a library yields an `excess` warning.
- R6 - Each Finding has Severity `error` or `warning`; a run fails only when at least one error exists. Accept: warnings only -> success exit code; any error -> failure exit code.
- R7 - Output is one line per Finding, `path:line: severity: rule-id: message`, with repo-relative paths, followed by one summary line. Accept: every output line matches that shape.
- R8 - Given a file argument, it reads the whole Workflow Folder but reports only that file's Findings. Accept: with Sessions A and B in conflict, a run on B reports only B's Finding.
- R9 - It never modifies files. Accept: the Workflow Folder is unchanged after any run.
- R10 - It runs offline and non-interactively from within the copied workflow folder on Windows and Linux. Accept: the same Workflow Folder yields identical Findings on both platforms with no prompts or downloads.
- R11 - brain-storm runs workflow-check on its new Session after writing, fixes all errors, and considers warnings before finishing. Accept: brain-storm never finishes with error Findings in its own Session.
- R12 - behavior-spec runs workflow-check while validating inputs and redirects to brain-storm when any error exists. Accept: a Workflow Folder with an error makes behavior-spec stop and redirect.

## Scope Guardrails
- in: Sessions and the Glossary; Rule Categories `structure`, `chain`, `vocabulary`, `excess`; wiring into brain-storm and behavior-spec.
- out: PRD and plan checking; meaning-level contradiction; modifying files; macOS.

## Constraints
- rule-based only; spends zero tokens.
- read-only; non-interactive; offline.
- travels inside the workflow folder alongside the skills; relies on one runtime common to dev machines and CI; no separate install step.
- platforms: Windows (primary dev) and Linux (CI).
- imposed format: Session format (`brain-storm/references/CONTEXT-FORMAT.md`) and Glossary format (`brain-storm/references/LANGUAGE-FORMAT.md`) - owner: brain-storm skill.
- quality need: output cheap for agents to read and readable for the developer.

## Success
- v1 succeeds when every Session accepted by behavior-spec passes with zero error Findings and behavior-spec no longer redirects for structural or chain problems.
- outcome (developer judgment): over the next few projects, replanning caused by missing, contradictory, or bloated workflow documents noticeably drops. This tests the premise that rule checks reduce replanning; if the direct signal holds but replanning does not drop, look to judgment-based review in the skills rather than more Rules.

## Decisions
- parked: PRD checking - quicker path to v1; PRD format likely changes after work-planner and qa-design exist.
- parked: plan checking - work-planner and its format do not exist yet.
- parked: `--strict` mode (warnings fail) - add only if evidence shows warnings are ignored.
- parked: macOS support - not a current concern.
- rejected: meaning-level contradiction detection - needs judgment and tokens; remains the skills' job.
- rejected: auto-fix - risk of silent wrong fixes; conflicts with never editing prior Sessions.
- rejected: separately installed tool or standalone binary - adds setup steps against portability.
- deferred-to-spec: R2-R5 - full Rule catalog with rule IDs, Category, and Severity per Rule.
- deferred-to-spec: R5 - size limits and the out-of-stage word list.
- deferred-to-spec: R6 - exit-code values.
- deferred-to-spec: R1 - outcome when the Workflow Folder is missing, empty, or has unreadable files.
- deferred-to-spec: R7, R10 - path separator and line-ending handling.
- deferred-to-spec: R3 - how the Session Chain is resolved (final, not superseded).

## Language
- New terms this session; full definitions in `language.md`.
- `workflow-check` - the command-line checker.
- `Rule` - one named check with rule ID, Category, Severity.
- `Finding` - one reported Rule break at a file and line.
- `Severity` - `error` or `warning`.
- `Category` - `structure`, `chain`, `vocabulary`, `excess`.
- `Session`, `Session Chain`, `Requirement`, `Glossary`, `Workflow Folder` - workflow document terms.
